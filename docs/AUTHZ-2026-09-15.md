# Can one signed-in person reach another's? 15 Sep 2026

The pen test on 10 September skipped authenticated testing, on the stated
grounds that the app had "no per-user data to confess across". That was true of
a two-person pantry in September. It stopped being true when kitchens, roles,
follows, blocks, private recipes and reports arrived, and nobody had gone back
to it. This is that pass.

**Scope:** every server action that takes the id of a row, every route under
`/api`, and the MCP endpoint. Authorised — Luna's own deployment, at her
request. Run against a clone rather than the live database.

**Result: three holes, all in recipes, all fixed in `0a01296`. Everything else
checked out.**

## 1. Anybody could delete anybody's recipe · serious · FIXED

`removeRecipe` in `app/recipes/actions.ts` had no authorisation of any kind: no
session check, no owner. It called `deleteRecipe(id)`, which was
`DELETE FROM recipes WHERE id = ?`.

Nothing in the UI calls it. That does not matter — **every exported function in
a `"use server"` file is a live HTTP endpoint**, reachable whether or not any
component references it. So any of the six accounts could delete any of the
eleven recipes by its id, and recipes cascade to their ingredients, their steps
and their cook history.

Demonstrated on a clone: the old statement removes another user's recipe by id
alone.

## 2. The same hole through the API · serious · FIXED

`DELETE /api/recipes/[id]` asked for no account at all and deleted by id. A
bearer token that could read the pantry could empty it of recipes.

## 3. Visibility mistaken for write permission · moderate · FIXED

`PUT /api/recipes/[id]` checked `getRecipe(id, viewer)` before saving, and so
did the editor's own `saveRecipeDocument`. That call answers "may this person
SEE it", which is not "may this person REWRITE it" — so anybody who could open
a recipe shared with them could overwrite its name, its ingredients and every
step.

## The fix, and why it is shaped that way

The author is in the `WHERE` clause of both the `DELETE` and the `UPDATE`,
which is the rule the stock writes already follow: an id belonging to somebody
else matches nothing, rather than being checked by a caller who might forget.
Both functions now *require* an author in their signature, so the compiler
refuses a caller that omits one — which is what caught the two remaining call
sites.

An `UPDATE` that matches nothing throws rather than returning quietly. The
worst outcome here is not refusing an edit; it is telling somebody their edit
saved when it did not, and losing their writing.

A refusal is reported as 404, not 403, so the API never confirms that somebody
else's private recipe exists.

## What was checked and found sound

- **50 id-taking server actions.** All gated and scoped. Five looked wrong to a
  first pass and were not: `moveReport`, `editCell` and `removeRow` are the
  admin database browser, gated by an `admin()` helper that checks
  `requireUser` then `isAdmin` and answers "Not found." to everyone else -
  unscoped is the point of a database browser. `addRecipeTag` and
  `removeRecipeTag` scope inside `tagRecipe`, which guards the insert with
  `EXISTS (SELECT 1 FROM recipes WHERE id = ? AND author_id = ?)`.
- **The stock writes.** `ADJUST_SQL`, `PACK_SQL` and the bulk actions all carry
  `kitchen_id` in the `WHERE`, as AGENTS.md says they must.
- **`/api` routes.** Everything except `/api/mcp/*`, `/api/nudge` and
  `/api/csp-report` sits behind the proxy's auth gate. The nudge checks
  `CRON_SECRET` itself; csp-report is deliberately open and writes nothing.
- **MCP.** Resolves its path token to a user and passes that user to every
  query. `saveRecipe(parsed.recipe, undefined, user.id)` — no existing id, so
  the endpoint can create a recipe and never overwrite one.

## Still not looked at

- **SQL injection.** Not attempted; the app uses parameterised statements
  throughout and the one place that builds SQL by hand
  (`recordMany` in `lib/usage.ts`) interpolates only a count of `(?, ?, ?)`
  placeholders, never a value.
- **Rate limiting on `/login`.** Still none, as the pen test said. The password
  is a 16-character random token, which is the right answer to that, but a
  limit would be belt and braces.
- **Blocks.** Whether a blocked person can still reach a blocker's content by
  id was not tested. `lib/notifications.ts` honours blocks; the feed and
  comment paths were read rather than exercised.
